# Задания

## Задание 1

```
Предложите решение для обеспечения процесса разработки: хранение исходного кода, непрерывная интеграция и непрерывная поставка. 
Решение может состоять из одного или нескольких программных продуктов и должно описывать способы и принципы их взаимодействия.

Решение должно соответствовать следующим требованиям:
- облачная система;
- система контроля версий Git;
- репозиторий на каждый сервис;
- запуск сборки по событию из системы контроля версий;
- запуск сборки по кнопке с указанием параметров;
- возможность привязать настройки к каждой сборке;
- возможность создания шаблонов для различных конфигураций сборок;
- возможность безопасного хранения секретных данных (пароли, ключи доступа);
- несколько конфигураций для сборки из одного репозитория;
- кастомные шаги при сборке;
- собственные докер-образы для сборки проектов;
- возможность развернуть агентов сборки на собственных серверах;
- возможность параллельного запуска нескольких сборок;
- возможность параллельного запуска тестов.

Обоснуйте свой выбор.
```

В качестве основной платформы предлагаю использовать **GitLab**, развернутый в Yandex Cloud. Для выполнения CI/CD использовать **GitLab Runner**, размещённые на собственных виртуальных машинах или в Kubernetes.

При этом GitLab будет отвечать за хранение исходного кода, управление репозиториями и запуск CI/CD, а GitLab Runner — непосредственно выполнять сборки и тесты.

### Архитектура

```text
Разработчик
     │
     ▼
   GitLab
     │
     │ Git push / Merge Request / Manual
     ▼
GitLab CI/CD
     │
     ▼
GitLab Runner
     │
     ├── Build
     ├── Unit tests
     ├── Integration tests
     ├── Docker build
     └── Deploy
             │
             ▼
     Container Registry
             │
             ▼
        Kubernetes
```

Для каждого микросервиса создаётся отдельный репозиторий:

```text
service-users
service-orders
service-payment
service-catalog
service-notifications
```

В каждом репозитории размещается конфигурация CI/CD. При этом общие этапы можно вынести в единые шаблоны и подключать их к разным проектам.

Типовой pipeline:

```text
Build
  ↓
Unit Tests
  ↓
Integration Tests
  ↓
Docker Build
  ↓
Push Image
  ↓
Deploy
```

Разные конфигурации сборки можно задавать с помощью переменных CI/CD. Это позволяет, например, отдельно запускать `dev`, `test` и `production` сборки из одного репозитория.

Секреты — пароли, токены, ключи и другие чувствительные данные — не должны храниться в Git. Для них используются защищённые переменные GitLab CI/CD или внешний Secret Manager.

Для параллельного выполнения используются несколько GitLab Runner. Например, тесты разных сервисов или различные наборы тестов могут выполняться одновременно.

### Обоснование выбора

GitLab позволяет объединить управление исходным кодом и CI/CD в одной системе. GitLab Runner можно размещать на собственных серверах, что соответствует требованию использовать собственные build-агенты.

Решение также хорошо подходит для микросервисной архитектуры: каждый сервис имеет собственный репозиторий и pipeline, а общие правила сборки можно реализовать через шаблоны.

## Задание 2

```
Предложите решение для обеспечения сбора и анализа логов сервисов в микросервисной архитектуре.
Решение может состоять из одного или нескольких программных продуктов и должно описывать способы и принципы их взаимодействия.

Решение должно соответствовать следующим требованиям:
- сбор логов в центральное хранилище со всех хостов, обслуживающих систему;
- минимальные требования к приложениям, сбор логов из stdout;
- гарантированная доставка логов до центрального хранилища;
- обеспечение поиска и фильтрации по записям логов;
- обеспечение пользовательского интерфейса с возможностью предоставления доступа разработчикам для поиска по записям логов;
- возможность дать ссылку на сохранённый поиск по записям логов.

Обоснуйте свой выбор.
```

Предлагаю использовать связку:

**Filebeat → Elasticsearch → Kibana**

Kibana является основным интерфейсом для работы с логами, а Elasticsearch отвечает за их централизованное хранение и поиск.

### Архитектура

```text
Микросервисы
     │
     │ stdout / stderr
     ▼
Docker / Kubernetes
     │
     ▼
  Filebeat
     │
     │ logs
     ▼
Elasticsearch
     │
     │ queries / visualizations
     ▼
  Kibana
```

**Filebeat** запускается на каждом хосте либо как DaemonSet в Kubernetes. Он собирает логи контейнеров и отправляет их в Elasticsearch.

Приложениям не требуется специальная интеграция с системой логирования: они просто записывают сообщения в `stdout/stderr`.

**Elasticsearch** используется как централизованное хранилище и поисковая система. В него поступают логи всех микросервисов.

Для удобства анализа к логам добавляются метаданные:

```text
timestamp
service
container
host
environment
level
message
```

Это позволяет выполнять поиск и фильтрацию, например:

```text
service = service-orders
level = ERROR
environment = production
```

или искать конкретный текст ошибки.

**Kibana** используется разработчиками для:

* поиска логов;
* фильтрации;
* анализа ошибок;
* сохранения поисковых запросов;
* предоставления ссылок на сохранённые представления.

Для повышения надёжности Filebeat использует буферизацию и повторную отправку при временной недоступности Elasticsearch. Это позволяет переживать кратковременные сбои центрального хранилища.

## Задание 3

```
Предложите решение для обеспечения сбора и анализа состояния хостов и сервисов в микросервисной архитектуре.
Решение может состоять из одного или нескольких программных продуктов и должно описывать способы и принципы их взаимодействия.

Решение должно соответствовать следующим требованиям:
- сбор метрик со всех хостов, обслуживающих систему;
- сбор метрик состояния ресурсов хостов: CPU, RAM, HDD, Network;
- сбор метрик потребляемых ресурсов для каждого сервиса: CPU, RAM, HDD, Network;
- сбор метрик, специфичных для каждого сервиса;
- пользовательский интерфейс с возможностью делать запросы и агрегировать информацию;
- пользовательский интерфейс с возможностью настраивать различные панели для отслеживания состояния системы.

Обоснуйте свой выбор.
```
Для мониторинга предлегаю использовать:

**Prometheus + Node Exporter + cAdvisor + Grafana**

### Архитектура

```text
                    ┌───────────────┐
                    │    Grafana    │
                    │               │
                    │  Dashboards   │
                    └───────┬───────┘
                            │
                            ▼
                       Prometheus
                            ▲
             ┌──────────────┼──────────────┐
             │              │              │
             │              │              │
             ▼              ▼              ▼
       Node Exporter    cAdvisor       /metrics
             │              │              │
             ▼              ▼              ▼
           Хосты       Контейнеры     Микросервисы
```

### Метрики хостов

Для мониторинга серверов используется **Node Exporter**.

Он предоставляет метрики, связанные с состоянием операционной системы:

* загрузка CPU;
* использование RAM;
* свободное и занятое дисковое пространство;
* операции с дисками;
* сетевой трафик;
* количество процессов;
* другие системные показатели.

Node Exporter устанавливается на каждый сервер, а Prometheus периодически получает с него метрики.

### Метрики контейнеров и сервисов

Для контроля ресурсов отдельных контейнеров используется **cAdvisor**.

Он позволяет получать показатели:

* CPU контейнера;
* RAM контейнера;
* сетевого трафика;
* дисковых операций;
* состояния контейнеров.

Например, можно определить, какой именно микросервис потребляет большую часть ресурсов:

```text
Server
 ├── service-users     CPU / RAM / Network
 ├── service-orders    CPU / RAM / Network
 ├── service-payment   CPU / RAM / Network
 └── service-catalog   CPU / RAM / Network
```

### Метрики приложений

Каждый микросервис предоставляет endpoint `/metrics` в формате Prometheus.

Например:

```text
http_requests_total
http_request_duration_seconds
orders_created_total
orders_failed_total
payments_total
```

Это позволяет контролировать не только состояние инфраструктуры, но и работу самого приложения.

Например:

* количество HTTP-запросов;
* количество ошибок;
* время ответа;
* количество созданных заказов;
* количество неуспешных платежей;
* другие специфичные для приложения показатели.

### Prometheus

Prometheus централизованно собирает метрики:

```text
Node Exporter ──┐
                │
cAdvisor ───────┼──→ Prometheus
                │
/metrics ───────┘
```

Prometheus используется для хранения метрик и выполнения запросов и агрегаций.

С его помощью можно определить:

* среднюю загрузку CPU;
* использование RAM;
* свободное дисковое пространство;
* сетевую нагрузку;
* количество запросов в секунду;
* процент ошибок;
* время ответа;
* нагрузку конкретного микросервиса.

### Grafana

Grafana используется как интерфейс для мониторинга метрик из Prometheus.

В ней создаются dashboards, например:

```text
┌──────────────────────────────────────────────┐
│              Infrastructure                 │
├──────────────┬──────────────┬───────────────┤
│ CPU          │ RAM          │ Disk          │
│   63%        │   71%        │   54%         │
├──────────────┴──────────────┴───────────────┤
│ Network traffic                              │
├─────────────────────────────────────────────┤
│ Service CPU / RAM                            │
├─────────────────────────────────────────────┤
│ HTTP requests / Errors / Response time       │
└─────────────────────────────────────────────┘
```
