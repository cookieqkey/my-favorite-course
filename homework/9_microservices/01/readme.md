# Задания

## Задание 1

```
Руководство крупного интернет-магазина, у которого постоянно растёт пользовательская база и количество заказов, рассматривает возможность переделки своей внутренней   ИТ-системы на основе микросервисов.
Вас пригласили в качестве консультанта для оценки целесообразности перехода на микросервисную архитектуру.
Опишите, какие выгоды может получить компания от перехода на микросервисную архитектуру и какие проблемы нужно решить в первую очередь.
```

### Переход интернет-магазина на микросервисную архитектуру

Переход на микросервисную архитектуру может быть целесообразен для крупного интернет-магазина, у которого постоянно растут количество пользователей и заказов. Однако микросервисы не решают проблемы автоматически и сами по себе усложняют инфраструктуру, поэтому переход должен быть постепенным.

#### Выгоды микросервисной архитектуры

1. **Масштабирование отдельных частей системы.**
   Можно независимо увеличивать количество экземпляров наиболее нагруженных сервисов. Например, сервис каталога может требовать значительно больше ресурсов, чем сервис управления профилями пользователей.

2. **Независимое развертывание.**
   Изменения в одном сервисе можно выпускать без необходимости разворачивать всю систему целиком. Это позволяет быстрее доставлять новые функции и исправления.

3. **Изоляция отказов.**
   Если один сервис выйдет из строя, остальные части системы могут продолжить работу. Например, временная недоступность сервиса рекомендаций не должна полностью блокировать оформление заказа.

4. **Разделение ответственности.**
   Каждый сервис отвечает за свою предметную область: пользователи, каталог товаров, корзина, заказы, платежи, доставка и т. д. Это упрощает разработку и сопровождение отдельных компонентов.

5. **Возможность использовать разные технологии.**
   Для разных сервисов можно выбирать наиболее подходящие языки программирования, базы данных и технологии, если это действительно оправдано.

6. **Упрощение работы команд.**
   Разные команды могут независимо заниматься своими сервисами, что особенно полезно при большом количестве разработчиков.

#### Какие проблемы нужно решить в первую очередь

1. **Правильно определить границы сервисов.**
   Нельзя просто разделить существующее приложение на большое количество маленьких сервисов. Необходимо определить независимые бизнес-домены и связи между ними.

2. **Организовать взаимодействие между сервисами.**
   Нужно выбрать способы обмена данными: HTTP/gRPC для синхронного взаимодействия и брокеры сообщений(очередей) для асинхронного. Также необходимо предусмотреть обработку таймаутов, повторных запросов и недоступности сервисов.

3. **Разделить данные и ответственность за базы данных.**
   Желательно, чтобы каждый сервис владел своими данными. При этом необходимо решить проблему согласованности данных между сервисами и разработать механизмы обработки распределённых операций.

4. **Настроить мониторинг и централизованное логирование.**
   В микросервисной системе становится значительно сложнее понять, где произошла ошибка. Поэтому нужны метрики, логи, трассировка запросов и система оповещений.

5. **Автоматизировать сборку и развертывание.**
   При увеличении количества сервисов ручное управление становится слишком сложным. Потребуются CI/CD, автоматические тесты, контейнеризация и инструменты оркестрации.

6. **Обеспечить безопасность.**
   Нужно организовать аутентификацию и авторизацию, безопасное взаимодействие сервисов, управление секретами и контроль доступа к данным.

7. **Подготовить команду и процессы.**
   Микросервисная архитектура требует новых компетенций в области распределённых систем, DevOps, мониторинга и эксплуатации.

#### Вывод

Для крупного интернет-магазина переход на микросервисную архитектуру может дать существенные преимущества: независимое масштабирование и развертывание, повышение отказоустойчивости и возможность параллельной работы нескольких команд.

При этом переход имеет смысл только при наличии реальных проблем монолитной системы, связанных с масштабированием, скоростью разработки или независимостью компонентов. Основные задачи перед переходом — определить границы сервисов, организовать взаимодействие и работу с данными, а также заранее подготовить мониторинг, логирование, CI/CD и безопасность.

Поэтому оптимальным подходом будет **постепенная миграция**, при которой наиболее независимые и проблемные части существующей системы выносятся в отдельные сервисы, а не переписывание всей системы сразу.
