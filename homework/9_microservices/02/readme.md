# Задания

## Задание 1

```
API Gateway

Предложите решение для обеспечения реализации API Gateway. Составьте сравнительную таблицу возможностей различных программных решений. На основе таблицы сделайте выбор решения.

Решение должно соответствовать следующим требованиям:
- маршрутизация запросов к нужному сервису на основе конфигурации,
- возможность проверки аутентификационной информации в запросах,
- обеспечение терминации HTTPS.

Обоснуйте свой выбор.

Для реализации API Gateway рассмотрим следующие решения:

* **Yandex API Gateway**;
* **Kong Gateway**;
* **NGINX**;
* **Traefik**.

Важно иметь возможность размещения инфраструктуры в российском облаке или непосредственно внутри собственной инфраструктуры компании, а также минимизировать зависимость от зарубежных SaaS-сервисов.

Yandex API Gateway конфигурируется декларативно с помощью OpenAPI 3.0. Маршруты определяются в спецификации, а запросы могут направляться на HTTP-сервисы. Кроме того, API Gateway позволяет подключать собственный домен и использовать сертификат из Yandex Certificate Manager для TLS.

Для проверки аутентификационной информации Yandex API Gateway поддерживает JWT. Gateway самостоятельно проверяет подпись токена, срок действия, `issuer`, `audience` и необходимые claims.

### Анализ решений

#### Yandex API Gateway

Главное преимущество Yandex API Gateway для нашего случая — **он является управляемым сервисом российской облачной платформы**.

Не требуется самостоятельно устанавливать, обновлять и обеспечивать отказоустойчивость API Gateway. Масштабирование выполняется самим сервисом.

Это особенно удобно для DevOps-команды: вместо эксплуатации отдельного кластера API Gateway необходимо управлять его конфигурацией и связанными ресурсами.

Yandex API Gateway также позволяет подключить собственную облачную сеть. В этом случае шлюз может взаимодействовать с ресурсами, находящимися в этой сети, например с виртуальными машинами и другими сервисами.

Создание и изменение API Gateway можно автоматизировать, в том числе через Terraform, что позволяет включить его в процесс Infrastructure as Code.

**Недостаток:** решение является частью Yandex Cloud. Если компания в будущем захочет полностью отказаться от Yandex Cloud или перенести систему в другой облачный/собственный контур, миграция потребует адаптации конфигурации.

#### Kong Gateway

Kong является полноценным специализированным API Gateway. Он позволяет централизованно организовать маршрутизацию запросов, аутентификацию и другие функции, необходимые для работы API.

Основные преимущества:

* маршрутизация запросов между микросервисами;
* поддержка различных механизмов аутентификации;
* терминация HTTPS;
* балансировка нагрузки;
* ограничение частоты запросов;
* ведение статистики и логирование;
* расширение возможностей с помощью плагинов;
* интеграция с контейнерной и Kubernetes-инфраструктурой.

Главное преимущество Kong перед Yandex API Gateway — **его можно самостоятельно развернуть в собственной инфраструктуре**, например в Kubernetes.

Однако в этом случае вся эксплуатационная нагрузка ложится на компанию: необходимо самостоятельно обеспечить обновления, отказоустойчивость, мониторинг и резервирование.

#### NGINX

NGINX отлично подходит для reverse proxy, маршрутизации, балансировки нагрузки и терминации HTTPS.

Однако для полноценного API Gateway потребуется больше дополнительной настройки. В частности, функции аутентификации и управления API менее естественно встроены в архитектуру NGINX, чем в специализированные API Gateway.

Поэтому NGINX я бы рассматривал скорее как **reverse proxy / ingress**, а не как основной API Gateway для крупной микросервисной системы.

#### Traefik

Traefik хорошо подходит для динамической контейнерной инфраструктуры и Kubernetes. Он удобно интегрируется с Kubernetes API и Gateway API, включая работу с TLS-маршрутами.

Его преимущество — простота эксплуатации в Kubernetes. Однако по набору возможностей управления API и аутентификации Kong выглядит более специализированным решением.

### Выбор решения

Если инфраструктура компании допускает использование Yandex Cloud я бы выбрал **Yandex API Gateway**.

Причины выбора:

1. **Российская облачная инфраструктура.**

2. **Минимум эксплуатационных затрат.**
   Yandex API Gateway является управляемым сервисом, поэтому компании не нужно самостоятельно обслуживать кластер API Gateway.

3. **Выполнение всех требований задания.**

   * маршрутизация — через OpenAPI-конфигурацию;
   * проверка аутентификации — поддерживается JWT;
   * терминация HTTPS — поддерживается через подключение домена и сертификата.

4. **Возможность Infrastructure as Code.**
   Конфигурацию можно создавать и изменять автоматически, в том числе используя Terraform.

### Итог

Выбор зависит от модели инфраструктуры:

| Условие                                        | Предпочтительный выбор |
| ---------------------------------------------- | ---------------------- |
| Компания готова использовать Yandex Cloud               | **Yandex API Gateway** |
| Нужен полностью самостоятельный deployment     | **Kong Gateway**       |
| Основная задача — reverse proxy/load balancing | **NGINX**              |
| Основная инфраструктура — Kubernetes           | **Traefik или Kong**   |

**В рамках поставленной задачи выбираю Yandex API Gateway.** Он удовлетворяет всем обязательным требованиям, при этом является управляемым сервисом российской облачной платформы, что снижает операционные затраты и упрощает эксплуатацию инфраструктуры в РФ.

При этом если компании **нельзя использовать публичное облако** и вся система должна находиться в собственном ЦОД, то выбор следует изменить на **Kong Gateway**, поскольку Yandex API Gateway нельзя самостоятельно развернуть внутри собственного контура.

```
Составьте таблицу возможностей различных брокеров сообщений. На основе таблицы сделайте обоснованный выбор решения.

Решение должно соответствовать следующим требованиям:
- поддержка кластеризации для обеспечения надёжности,
- хранение сообщений на диске в процессе доставки,
- высокая скорость работы,
- поддержка различных форматов сообщений,
- разделение прав доступа к различным потокам сообщений,
- простота эксплуатации.

Для организации асинхронного взаимодействия микросервисов рассмотрим следующие решения:

* RabbitMQ;
* Apache Kafka;
* Yandex Message Queue.

Брокер сообщений необходим для организации взаимодействия между микросервисами без жёсткой зависимости от доступности каждого сервиса в конкретный момент времени.

Например, после оформления заказа сервис заказов может отправить сообщение в очередь, а сервис доставки или уведомлений обработает его позже. Это позволяет разгрузить сервисы, повысить отказоустойчивость и организовать асинхронную обработку.

### Выбор решения

Для данной задачи предлагаю использовать **RabbitMQ**.

RabbitMQ является наиболее подходящим вариантом для типичного взаимодействия микросервисов, поскольку одновременно предоставляет:

* кластеризацию и механизмы отказоустойчивости;
* сохранение сообщений на диске;
* высокую производительность;
* очереди и маршрутизацию сообщений;
* поддержку различных форматов данных;
* разграничение прав доступа;
* относительно простую эксплуатацию.

В отличие от Kafka, RabbitMQ не требует сложной инфраструктуры для типичных сценариев обмена сообщениями между микросервисами.

Yandex Message Queue также можно использовать совместно с Yandex API Gateway, если компания хочет максимально использовать управляемые сервисы Yandex Cloud. Однако это создаёт более сильную зависимость от конкретного облачного провайдера.

Даже если для внешнего API используется Yandex API Gateway, для внутреннего взаимодействия микросервисов целесообразно использовать RabbitMQ.

RabbitMQ можно развернуть в Yandex Cloud самостоятельно, например на виртуальных машинах или в Kubernetes, а при необходимости перенести в другой российский облачный провайдер или собственный ЦОД.

### Почему не Kafka

Kafka имеет очень высокую производительность и особенно хорошо подходит для больших потоков событий и длительного хранения данных.

Однако для стандартного обмена командами и событиями между микросервисами её возможности могут быть избыточными, а эксплуатация сложнее. Поэтому при отсутствии требований к очень большим потокам данных предпочтительнее RabbitMQ.
