# Расчёт ресурсов Kubernetes-кластера

## 1. Исходные данные

Проект включает базу данных, систему кеширования, frontend и backend.
Приложение упаковывается в Helm-чарт для деплоя в разные окружения.

```
  Компонент       Количество реплик   CPU на реплику   RAM на реплику
  ------------- ------------------- ---------------- ----------------
  База данных                     3           1 vCPU             4 ГБ
  Кеш                             3           1 vCPU             4 ГБ
  Frontend                        5         0.2 vCPU            50 МБ
  Backend                        10           1 vCPU           600 МБ
```

Для расчёта указанные значения считаются потреблением ресурсов одной
реплики. В Kubernetes следует задавать `requests` и `limits`, а также
предусмотреть ресурсы для системных компонентов и запас на отказ ноды.

## 2. Расчёт потребления приложением

### База данных

CPU:

`3 × 1 = 3 vCPU`

RAM:

`3 × 4 = 12 ГБ`

### Кеш

CPU:

`3 × 1 = 3 vCPU`

RAM:

`3 × 4 = 12 ГБ`

### Frontend

CPU:

`5 × 0.2 = 1 vCPU`

RAM:

`5 × 50 МБ = 250 МБ = 0.25 ГБ`

### Backend

CPU:

`10 × 1 = 10 vCPU`

RAM:

`10 × 600 МБ = 6000 МБ ≈ 5.86 ГБ`

### Общий итог

CPU:

`3 + 3 + 1 + 10 = 17 vCPU`

RAM:

`12 + 12 + 0.25 + 5.86 = 30.11 ГБ`

**Минимальная потребность приложения: 17 vCPU и около 30.11 ГБ RAM.**

Это суммарная нагрузка всех указанных реплик без учёта служебных
ресурсов Kubernetes и отказа ноды.

## 3. Добавление запаса ресурсов

Для production-кластера необходимо оставить ресурсы для:

-   операционной системы;
-   kubelet и container runtime;
-   CNI и сетевых компонентов;
-   CoreDNS;
-   мониторинга и логирования;
-   временного увеличения потребления ресурсов.

Примем запас в 20% для нагрузки приложения.

CPU с запасом:

`17 × 1.2 = 20.4 vCPU`

RAM с запасом:

`30.11 × 1.2 ≈ 36.13 ГБ`

Таким образом, необходимо обеспечить примерно **20.4 vCPU и 36.13 ГБ
RAM** под workload с 20-процентным запасом.

## 4. Расчёт количества worker-нод

Выберем конфигурацию одной worker-ноды:

```
  Параметр          Значение
  ------------ -------------
  CPU                 8 vCPU
  RAM                  16 ГБ
  Диск            100 ГБ SSD
  Назначение     Worker node
```

Предположим, что на каждой worker-ноде резервируется под системные
нужды:

```
  Ресурс     Резерв на одной ноде
  -------- ----------------------
  CPU                    1.5 vCPU
  RAM                        4 ГБ
```

Доступные ресурсы одной worker-ноды:

CPU:

`8 − 1.5 = 6.5 vCPU`

RAM:

`16 − 4 = 12 ГБ`

### Учитываем выход из строя одной ноды

Для отказоустойчивости используем схему N+1: кластер должен выдержать
потерю одной worker-ноды.

При наличии 5 worker-нод после отказа одной останутся 4 ноды.

Доступный CPU после отказа:

`4 × 6.5 = 26 vCPU`

Доступная RAM после отказа:

`4 × 12 = 48 ГБ`

```
  -------------------------------------------------------------------------
  Ресурс                 Потребность с       Доступно после Результат
                           запасом 20%    отказа одной ноды 
  --------------- -------------------- -------------------- ---------------
  CPU                        20.4 vCPU              26 vCPU Достаточно

  RAM                         36.13 ГБ                48 ГБ Достаточно
  -------------------------------------------------------------------------
```

**Вывод: 5 worker-нод выбранной конфигурации достаточно**, чтобы
сохранить рассчитанную capacity после отказа одной worker-ноды при
условии корректного распределения Pod и доступности хранилища.

## 5. Управляющие ноды Kubernetes

Для отказоустойчивого Kubernetes-кластера предусмотрим 3
control-plane-ноды.

```
  Параметр                                                                Значение
  ------------------------------ -------------------------------------------------
  Количество control-plane-нод                                                   3
  CPU каждой ноды                                                           4 vCPU
  RAM каждой ноды                                                             8 ГБ
  Диск каждой ноды                                                  50--100 ГБ SSD
  Назначение                       API Server, Scheduler, Controller Manager, etcd
```

Три управляющие ноды позволяют пережить отказ одной управляющей ноды при
корректно настроенной HA-конфигурации Kubernetes и etcd.

В расчёте workload ресурсы control-plane-нод не учитываются:
предполагается, что прикладные Pod размещаются на worker-нодах.

## 6. Итоговая конфигурация кластера

**Итого: 8 Kubernetes-нод.**

```
  -----------------------------------------------------------------------
  Тип ноды        Количество CPU одной ноды RAM одной ноды     Диск одной
                                                                     ноды
  ----------- -------------- -------------- -------------- --------------
  Control                  3         4 vCPU           8 ГБ 50--100 ГБ SSD
  Plane                                                    

  Worker                   5         8 vCPU          16 ГБ     100 ГБ SSD
  -----------------------------------------------------------------------
```

### Суммарные физические ресурсы

Control Plane:

-   CPU: `3 × 4 = 12 vCPU`
-   RAM: `3 × 8 = 24 ГБ`

Worker:

-   CPU: `5 × 8 = 40 vCPU`
-   RAM: `5 × 16 = 80 ГБ`

Всего по кластеру:

-   **CPU: 52 vCPU**
-   **RAM: 104 ГБ**
-   **Количество нод: 8**

Суммарные физические ресурсы нод не равны allocatable ресурсам для
приложений, так как часть ресурсов резервируется для ОС и Kubernetes.

## 7. Требования к отказоустойчивости и хранению данных

Для обеспечения отказоустойчивости базы данных и кеша необходимо
предусмотреть:

-   База данных --- 3 реплики, распределённые по разным worker-нодам.
-   Кеш --- 3 реплики, распределённые по разным worker-нодам.
-   StatefulSet для stateful-компонентов.
-   PersistentVolume и StorageClass для хранения данных базы.
-   Настройку автоматического переключения на реплику при отказе
    основного экземпляра БД.
-   Redis Sentinel или Redis Cluster для отказоустойчивого кеша, если
    используется Redis.
-   PodDisruptionBudget и pod anti-affinity либо topology spread
    constraints для распределения реплик.
-   Резервное копирование базы данных на отдельное хранилище.

Объём дисков для БД в исходных условиях не задан. Поэтому 100 ГБ SSD на
worker-ноде --- предварительный размер диска ноды. PersistentVolume для
базы данных необходимо рассчитывать отдельно, учитывая объём данных,
рост базы, WAL и требования к резервному копированию.

## Заключение

Для проекта с отказоустойчивой базой данных, кешем, frontend и backend
предлагается Kubernetes-кластер из **8 нод**:

-   **3 control-plane-ноды** по 4 vCPU и 8 ГБ RAM;
-   **5 worker-нод** по 8 vCPU и 16 ГБ RAM.

Расчётная потребность приложения составляет 17 vCPU и около 30.11 ГБ
RAM. С 20-процентным запасом --- 20.4 vCPU и около 36.13 ГБ RAM.

После отказа одной worker-ноды остаётся 26 vCPU и 48 ГБ allocatable
ресурсов, что превышает рассчитанную потребность.

Это предварительный sizing. Окончательная конфигурация должна уточняться
нагрузочными тестами, требованиями к persistent storage, реальным
потреблением системных компонентов и настройками requests/limits.
